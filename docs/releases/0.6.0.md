# Upgrading to trembita 0.6.0

**Target:** apps on **0.5.x** moving to **0.6.0** (pre-1.0 minor — breaking changes are expected).

**Summary:** 0.6 is the **capability platform** release: typed ops (`CapGroup` / `CapOp`), macros (`#[cap_handler]`, `cap_register_chain!`), richer `OpCtx`, gateway helpers, queued idempotency, scaffold/doctor parity, plus **facade layering** (`trembita-assembly`, `trembita-showcase` as workspace-only crates).

Full changelog: [archive/CHANGELOG-pre-1.0.md § 0.6.0](../archive/CHANGELOG-pre-1.0.md#060--2026-09-16).

---

## 1. Cargo.toml

Bump the synchronized workspace version on the facade:

```toml
trembita = { version = "0.6", features = ["http-jobs", "dev-certs"] }
```

All published `trembita-*` crates share **0.6.0** on crates.io ([library-and-publishing](../decisions/library-and-publishing.md)).

**Do not** add dependencies on **`trembita-assembly`** or **`trembita-showcase`** in product apps — they are `publish = false` and not part of the semver product surface ([facade-layering](../decisions/facade-layering.md)).

---

## 2. Registration: prefer `AppManifest` + `TrembitaConfigure`

0.6 docs and scaffolds treat **[`AppManifest`](../../crates/trembita/src/app/manifest.rs)** as the single registry for jobs, topics, workers, workflows, and **capabilities**, wired via **[`.manifest()`](../../crates/trembita/src/app/builder.rs)**.

Use **[`TrembitaConfigure`](../../crates/trembita/src/configure.rs)** (or `TrembitaApp::from_env`) for **data directory**, HTTP/gateway options, and env merge — not ad-hoc builder chaining that was never stable public API.

| Before (0.5 examples / old snippets) | After (0.6) |
|--------------------------------------|-------------|
| `.jobs(…)` / `.data_dir(…)` on builder in app code | `AppManifest { … }` + `.manifest(&manifest)`; `TrembitaConfigure::with_data_dir(…)` or `TREMBITA_DATA_DIR` |
| Manual capability wiring only in `app.rs` | `src/capabilities/` + `manifest.rs` with `CapManifest` / `cap_register_chain!` |

See [getting-started.md](../getting-started.md) and [scenarios/capabilities.md](../scenarios/capabilities.md).

## 3. Capability macros

### `#[cap_request]`

The **`op = "…"`** attribute was **removed**. The operation name is derived from the struct identifier (PascalCase → snake_case), same as handler routing.

```rust
// 0.5
#[cap_request(group = "orders", op = "fulfill")]
pub struct Fulfill { /* … */ }

// 0.6
#[cap_request(group = "orders")]
pub struct Fulfill { /* … */ }
```

### `#[cap_handler]`

Handlers may be **`async`**. Use **`cap_register_chain!`** in the group module or manifest to register ops on a `CapManifest`.

Scaffold templates under `trembita new` emit **`capabilities/ping`** and **`capabilities/onboarding`** as reference patterns.

## 4. Handler context (`OpCtx`)

New helpers for product handlers ([capability-dx](../decisions/capability-dx.md), B-27):

| API | Purpose |
|-----|---------|
| [`OpCtx::deps`](../../crates/trembita/src/capability/deps.rs) / **`.cap_deps()`** on builder | Inject app services into handlers via [`CapDeps`](../../crates/trembita/src/capability/deps.rs) |
| [`OpCtx::store`](../../crates/trembita/src/capability/ctx.rs) / **`require_store`** | Durable group state via [`trembita::capstore`](../../crates/trembita/src/capstore.rs) (crate: `trembita-actor-store`) |
| [`OpCtx::ingress`](../../crates/trembita/src/capability/ingress.rs) | Request metadata from wire + HTTP headers |
| [`CapError::domain`](../../crates/trembita/src/capability/error.rs) | Maps to **HTTP 400** on gateway routes |

Queued capabilities: use gateway **[`cap_queued_wait`](../../crates/trembita/src/gateway/cap_handlers.rs)** / **[`cap_schedule`](../../crates/trembita/src/gateway/cap_handlers.rs)**; **`dedup_key`** bridges to job idempotency ([background-jobs](../scenarios/background-jobs.md)).

## 5. Layout and tooling

- Default product layout: **`src/capabilities/<group>/`** + optional **`src/domain/`** (no trembita imports).
- **`trembita doctor`** checks capability folders and queued wiring ([framework-conventions](../decisions/framework-conventions.md)).
- Showcases: [examples/](../../examples/README.md) (`background-jobs`, `stateful-workers`, `realtime`, `workflows`) updated for capabilities.

---

## 6. Platform features (no app migration required)

These ship in 0.6 but do not require code changes unless you opt in:

- **Scheduled workflows / work triggers** — Meta-Raft scheduled dispatch ([workflows scenario](../scenarios/workflows.md)).
- **mTLS certificate hot-reload** — `PemSecurity`, `CertReloadHandle`; cluster discovery refinements.
- **`TrembitaConfigure`** — additional HTTP/API surface configuration alongside env boot.
- **Deployment docs** — VPS / library-first guidance; orchestrator-specific runbooks are out of scope ([deployment-model](../decisions/deployment-model.md)).

---

## 7. Maintainers and fork authors

| Change | Action |
|--------|--------|
| Cluster boot moved to **`trembita-assembly`** | Update internal imports; product code stays on **`trembita::`** re-exports |
| Benches/soaks / custom SM demos | Use **`trembita-showcase`** (`cluster_builder`, bins under `showcase-*`) |
| **`parse_enqueue_body`** | No longer a public export from `trembita-http` — use product enqueue APIs |
| Publish dry-run | Leaf crate dry-run skips when **`trembita`** depends on unpublished **`trembita-assembly`** — run full **`./scripts/release.sh 0.6.0 --publish`** for a real upload |

## 8. Verify after upgrade

```bash
cargo update -p trembita
cargo check
trembita doctor --preflight   # if using trembita-cli
```

Run your usual integration tests; for framework contributors: `./scripts/gate.sh --tier push`.

**Still deferred (not 0.6):** crate rename `trembita-actor-store` → `trembita-capstore` (alias only), OpenAPI for capabilities ([backlog](../backlog.md)).
